# Azure DevOps tracker (Azure Repos and Azure Boards)

The `azure_devops` tracker connects Preloop to **Azure DevOps Services**
(`https://dev.azure.com`). It reviews Azure Repos pull requests and treats
Azure Boards work items as issues (see [Azure Boards work
items](#azure-boards-work-items)). Pull request review works like this:

1. A pull request is created, or its source branch gets a new commit.
2. Azure DevOps sends a service hook to Preloop.
3. Preloop starts the flows triggered by `pull_request_opened` or
   `pull_request_updated` on that repository, such as the Pull Request
   Reviewer.
4. File findings appear on changed lines, alongside one summary thread updated on each run.

The tracker hosts repositories, like GitHub, GitLab and Bitbucket trackers,
and syncs the work items of each Azure DevOps project as issues.

## Before you start

You need:

- an Azure DevOps organization at `https://dev.azure.com/{organization}`;
- a personal access token (PAT) for a user who can read the repositories;
- a public HTTPS `PRELOOP_URL` on the Preloop deployment, so Azure DevOps can
  reach the callback URL.

## Personal access token scopes

Create the PAT under **User settings > Personal access tokens** with
**Organization** set to your organization (not "All accessible
organizations" unless you need it) and these custom scopes:

| Scope | Access | Why |
| --- | --- | --- |
| Code | Read | List repositories, read pull requests and changed files, clone the repository. |
| Pull Request Threads | Read & write | Post the review as a comment thread. |
| Work Items | Read & write | Sync, search, create and update work items, comment on them and link pull requests. Read alone is enough for triggers and sync. |
| Code | Read & write | Optional. Required to vote when **Cast the token owner's vote** is enabled. With voting disabled, the decision appears only in the summary. |

There is no separate **Service Hooks (Read, write & manage)** checkbox to
select in the PAT screen. **Service Connections** is unrelated. The
[Subscriptions API](https://learn.microsoft.com/en-us/rest/api/azure/devops/hooks/subscriptions/create?view=azure-devops-rest-7.1)
lists the event's resource scope: `vso.code` (Code Read) for repository
events, `vso.work` (Work Items Read) for work item events, and `vso.build`
for build events. The `vso.hooks_write` name in the OAuth/extension scope
catalog is not a PAT-screen instruction.

The user also needs the project's **View subscriptions** and **Edit
subscriptions** service-hook permissions; Project Administrators have
these by default. An administrator can delegate them to another user or
group. Token scopes do not grant project permissions. See Microsoft's
[service-hook permissions](https://learn.microsoft.com/en-us/azure/devops/service-hooks/overview?view=azure-devops#prerequisites).
Availability depends on project permissions and organization token policy. If **Register** returns permission denied, use
[Manual setup](#manual-setup) with an authorized project user; do not broaden
the token to Full access just to find a missing checkbox.

Set a PAT expiry and replace the token in the tracker before it expires.

## Add the tracker

1. In the console open **Trackers > Add tracker** and choose **Azure DevOps**.
2. **Organization**: the name in `https://dev.azure.com/{organization}`, for
   example `example-org`. Enter the name only, not a URL.
3. **Project** (optional): an Azure DevOps project name. Only repositories in
   that project are listed.
4. **Repository** (optional): a repository name in that project. Requires a
   project.
5. **Personal access token**: the PAT from above. Use a dedicated Azure DevOps
   user named for Preloop, with access only to the required repositories.
   Azure displays the token owner's identity on every comment; Preloop cannot
   impersonate a different author. Every posted thread starts with
   **Generated by Preloop**.
6. **Cast the token owner's vote**: off for new trackers. Enable it only if
   Preloop should set that user's vote (`10` approved, `-5` waiting for author).
   Existing Azure trackers retain voting through the migration default;
   edit the tracker to turn it off. With voting off, approve/request changes
   are expressed in the summary and no vote API is called.
7. Select **Next**. Preloop tests the connection and lists the repositories,
   grouped by Azure DevOps project. Check the repositories you want (or
   **Select All**) and save. Entering a project filters discovery; it does
   not select repositories. An empty selection cannot be saved.

If the tracker shows **0 repositories imported**, its page explains whether
no organization is included or a sync/access check is needed. Edit the
scope and select **Sync Now**.

### How Azure DevOps maps to Preloop

| Azure DevOps | Preloop |
| --- | --- |
| Organization | Organization |
| Project | Group shown in the repository list |
| Git repository (Azure Repos) | Project |
| Work item (Azure Boards) | Issue of one repository's project (see below) |

Each Azure Repos git repository becomes one Preloop project. Flows, review
policies and scope rules attach to repositories.

## Service hooks

Preloop receives events through seven **Web Hooks** service hook
subscriptions on the Azure DevOps project:

- `git.pullrequest.created` (Pull request created)
- `git.pullrequest.updated` (Pull request updated): separate source-push and lifecycle subscriptions
- `ms.vss-code.git-pullrequest-comment-event` (Pull request commented on)
- `workitem.created` (Work item created)
- `workitem.updated` (Work item updated)
- `workitem.commented` (Work item commented on)

The callback URL is:

```text
{PRELOOP_URL}/api/v1/private/webhooks/azure_devops/{tracker_id}
```

The tracker page shows the exact callback URL, whether a secret is set and
the registration state.

### Generate the secret

Open the tracker page and select **Generate secret** in the **Azure DevOps
service hooks** panel. The secret is shown once; copy it if you plan to set
the subscriptions up by hand. **Rotate secret** replaces it; update the
subscriptions afterwards (register again, or edit the header by hand).

### Automatic setup

With the resource scopes and project permissions above, select **Register** (a secret is generated first if the tracker has
none). Preloop creates the subscriptions with the secret header. The pull
request ones are filtered to the tracker's repository (or its project when
no repository is selected). Separate `Pull request updated` subscriptions cover
source pushes and lifecycle changes. Lifecycle deliveries carry
`X-Preloop-Azure-Lifecycle:true` and can stop reviews, never start them. The
work item ones cover the whole project. Registering also stores
the token owner's identity and the project's state categories on the
tracker (see [Work item events](#work-item-events)). Registering again updates Preloop's subscriptions in place and never
touches others. The panel then shows
`registered` and the subscription ids. **Check** reads the current state from
Azure DevOps.

### Manual setup

A project administrator, or a user with delegated subscription permissions,
can create the subscriptions instead. Use this path if automatic registration
is unavailable:

1. Open **Project settings > Service hooks** and select **Create
   subscription**.
2. Choose **Web Hooks** and select **Next**.
3. Trigger: **Pull request created**. Filter by **Repository** (and
   optionally target branch). Select **Next**.
4. Action settings:
   - **URL**: the callback URL from the tracker page.
   - **HTTP headers**: `X-Preloop-Webhook-Secret:<secret>`
   - **Resource details to send**: All
   - **Messages to send** and **Detailed messages to send**: None (not
     needed)
   - **Resource version**: 1.0
5. For created/updated PR subscriptions, select **Test**, then **Finish**. A passing Test
   checks the callback URL and secret header. Azure sends a canned sample;
   Preloop responds `200` with `test_notification` and starts no review.
   It does not prove repository scope or flow configuration. A missing or
   wrong secret still fails. For work item subscriptions, finish the setup
   and verify with an actual work item event.
6. Repeat for **Pull request updated**, with **Change** set to **Source branch
   updated**. Keep this filter: metadata edits must not start reviews.
7. Add a second **Pull request updated** subscription with **Change** set to
   **Pull request lifecycle status changed**. Send both the secret header and
   the additional header `X-Preloop-Azure-Lifecycle:true` (one header per line).
   This subscription stops reviews on abandon/complete and never starts one.
   Existing setups need this additional subscription; **Register** adds it.
8. For comment commands, repeat for **Pull request commented on** with the same
   repository and action settings. Finish and verify using a real command.
9. Repeat for **Work item created**, **Work item updated** and **Work item
   commented on**, without filters.

After a manual setup, select **Register** once if the token allows it, or
the loop guard below has no token identity to compare with.

Repeat per repository if you filter by repository and several are in scope.

### Delivery checks

- Deliveries without the `X-Preloop-Webhook-Secret` header, or with a value
  that does not match the tracker's secret, are rejected with an
  authentication error and start no flow. A tracker without a secret accepts
  no deliveries.
- Authenticated deliveries for the correct organization but a repository
  that is not imported or outside the selected scope return `200` and start
  no flow. The tracker page shows the last ignored reason. This avoids
  subscription failures and retries for intentional scope exclusions.
  Real events for another organization still return `403`.
- Before starting a review, Preloop reads the PR's current state and head.
  A delayed event for an abandoned/completed PR or an older commit is skipped.
  Abandon/complete notifications also stop runs still working on that PR.
- Pull request updates that do not change the source commit (votes,
  reviewers, comments, title or description edits) are ignored. Only a new
  push to the source branch produces an automatic `pull_request_updated`, so a review is
  not repeated for unrelated changes.

## Review the pull requests

Create a flow from the **Pull Request Reviewer** preset, pick this tracker
and repository as the trigger, and keep the events `pull_request_opened` and
`pull_request_updated`. The agent gets the repository cloned at the pull
request's source commit with the tracker's PAT (supplied through a git
credential file, never in the clone URL) and posts its review as a pull
request review. File findings use `threadContext` with right-side line/offset
coordinates and `pullRequestThreadContext` with the reviewed iteration and
`changeTrackingId`. The reviewed SHA marker pins positions even when another
push arrives during publication. Azure tracks those anchors across iterations.
Incremental reviews update the existing comment IDs and set threads to `fixed`
or `active` as findings are addressed or persist.

Preloop validates positions using the iteration's immutable common/source
commits. Deleted or renamed files, lines outside the changed ranges, unavailable
file contents and positions rejected by Azure fall back to general threads with
`path:line`; findings are retained. Left-side positions also fall back.

There is one marked summary thread per PR, updated in place on every run.
The brief review notice becomes a reply in that summary instead of creating a
separate thread; the previous details and checked boxes survive until the full
summary is updated. The hidden markers identify Preloop comments even when the
PAT owner's name is displayed. API clients can set the preference through
`connection_details.cast_token_owner_vote` (a boolean).

### Ask for a review again

On an active PR, add the **preloop-review** label or post a comment containing
only **/preloop review** (case-insensitive; surrounding whitespace is ignored).
Both request a review of the current head. In the flow's trigger settings you
can change or disable the label and disable the comment command independently.
The flow must subscribe to **Pull Request Updated** for this repository.

Azure accepts free-form PR labels, but label changes do not emit a service hook.
The sync scheduler publishes a review-request tick every 15 seconds; a sync
worker must be running to consume it. Hook registration alone does not start
label discovery. Each tick leases at most two imported repositories and reads
five active PRs per repository, rotating pages. A repository is eligible again
after 30 seconds. A matching flow can name the tracker or use any source, and
must belong to the same account and include the repository in its project scope.
Paused flows are polled too, so a request can report **flow paused**.

With a stable set of `R` active imported repositories with matching flows across
the installation (including candidates skipped by scope checks) and `N` active
PRs in the requested repository, the worst-case discovery interval is
`15 × max(2, ceil(R / 2)) × max(1, ceil(N / 5))` seconds, plus API/worker processing
time. For one or two repositories with at most five active PRs each, this is
30 seconds plus processing time. After acceptance, allow up to another 30
seconds for the 15-second quiet window and next scheduler tick. An existing
review must finish before its follow-up starts. These bounds assume the
scheduler and worker keep up and Azure responds successfully; outages, rate
limits, and a changing PR list can extend them.

On the tracker page, **Azure DevOps service hooks** shows the last label poll,
poll failures, and the ten most recent request outcomes (with PR, flow and time).
Use **Check** to refresh it. **Not polled yet** means no label discovery attempt
has been recorded: check that the scheduler/worker run and that an imported,
included repository has a flow subscribed to Pull Request Updated. **Filter mismatch**,
**flow paused**, and **pull request not active** explain requests that were seen
but did not run. A rejected label stays attached. Both request paths refresh
`draft`, `state`, author and branch filters from the live PR, so `draft=false`
still excludes drafts and `state=open` still excludes closed PRs.

Comments use the **Pull request commented on** hook (`ms.vss-code.git-pullrequest-comment-event`). Add that comment
subscription using the same repository, callback and secret settings. Verify
it with a real command; the canned Test support covers created/updated only.

Accepted labels are removed when the token has Code write access and permission
to edit the PR. If removal is denied, remove the label, allow a polling cycle to
observe its absence, then re-add it for another request. A label left attached
does not continually start reviews. Repeated commands and labels are coalesced
for a short quiet window; while a review runs, at most one follow-up is pending
per flow and PR. Closed PRs are skipped; explicit requests use the current head when dispatched.

Preloop's own comments and review threads never request another review.
Title/description edits, votes, reviewer changes and unrelated labels do not
request reviews. You can also use **Run reviewer** in the tracker's **Pull
requests** tab to select a reviewer flow explicitly.

## Azure Boards work items

Work items are the tracker's issues, at the level of Jira and GitHub issues:
issue-triggered flows (triage, implementation) start on them, and the MCP
issue tools (`get_issue`, `create_issue`, `update_issue`, `add_comment`,
`update_comment`) accept a work item URL such as
`https://dev.azure.com/{organization}/{project}/_workitems/edit/{id}` or its
key.

### Which Preloop project holds the work items

A work item belongs to an Azure DevOps **project**, while a Preloop project is
one **repository**. Each Azure DevOps project's work items attach to one of
its repositories, chosen in this order:

1. `connection_details.work_item_repositories`, a map of Azure DevOps project
   name to repository name, when it names the project;
2. the tracker's repository, when the tracker is bound to one;
3. the project's only repository;
4. the repository named like the project (the repository Azure DevOps
   creates with a new project).

A project with one repository, or with its default repository, needs no
configuration. When none of the rules picks a repository (several
repositories, none named like the project, no override), its work items are
not synced and their events are acknowledged without starting a flow. Set
the override through the trackers API (`PUT /api/v1/trackers/{id}` with
`connection_details.work_item_repositories`); there is no form field for it
yet. Every work item is stored once, under that repository, and an
implementation flow clones that repository.

### Field mapping

| Azure Boards | Preloop issue |
| --- | --- |
| Work item id | External id; key `{organization}/{project}#{id}` |
| `System.Title` | Title |
| `System.Description` (HTML) | Description (markdown, see below) |
| `System.State` | Status name; open or closed through its state category |
| `System.WorkItemType` | Issue type (`bug`, `feature`, `task`) and the type name |
| `System.AssignedTo` | Assignee |
| `System.CreatedBy` | Reporter |
| `System.Tags` | Labels |
| `Microsoft.VSTS.Common.Priority` | Priority 1 Highest, 2 High, 3 Medium, 4 Low, when the type has it |
| Parent / child, related, predecessor / successor, duplicate links | Relations (`parent`, `child`, `relates_to`, `blocks`, `blocked_by`, `duplicates`, `duplicated_by`) |
| Comments | Comments (markdown) |

**Open or closed** comes from the state's category, never from its name, so
any process (Basic, Agile, Scrum, CMMI, inherited) and any language works:
states in the `Completed` or `Removed` category are closed, all others
(`Proposed`, `InProgress`, `Resolved`) are open. Setting the status `closed`
moves the item to the first `Completed` state of its type, `open` to the
first `Proposed` state; any state name of the type is accepted too.

**New work items** get the requirement type of the project's process (Issue,
User Story, Product Backlog Item or Requirement) unless
`custom_fields.work_item_type` names another. Other `custom_fields` named
like `Namespace.Field` are written as fields.

**Rich text.** Descriptions and comments are HTML in Azure Boards and
markdown in Preloop. Headings, paragraphs, line breaks, bold, italic,
strikethrough, inline code, code blocks, links, nested lists, quotes and
rules convert both ways without loss. Lossy: styling (colours, fonts,
alignment) is dropped; tables become `a | b` text lines; images become
`![alt](src)`; `@mentions` become their display text; markdown tables, task
lists and raw HTML in markdown are shown literally, not rendered. A field
already stored in Azure's Markdown format is read as is.

### Work item events

| Service hook | Preloop event |
| --- | --- |
| `workitem.created` | `issue_opened` |
| `workitem.updated` | `issue_labeled` when a tag was added, else `issue_status_changed` when the state changed, else `issue_unlabeled` when a tag was removed, else `issue_updated`. A mixed edit also starts flows on the other types it carries, as for Jira. |
| `workitem.commented` | `comment_created` |

Label filters (`labels`, `labels_all`), the priority, assignee and author
filters, and `status_from` / `status_to` work as for Jira. Each work item
revision is processed once per event type, so a retried delivery starts no
second run.

**No self-trigger loops.** Changes made with the tracker's own token (a flow
updating or commenting on its work item) are stored but start no flow,
except a tag change, which is the hand-off from triage to implementation as
on every other tracker. Preloop recognises its own changes by the token
owner's identity, recorded when you select **Register**; after replacing the
PAT, select **Register** again. Use a token of a dedicated user: changes a
person makes with the same token are treated as Preloop's own.

### Linking pull requests

When a flow triggered by a work item records an opened Azure Repos pull
request, Preloop adds it to the work item's **Development** section (an
artifact link). Flows that review a pull request were triggered by the pull
request, not a work item, and add no link.

## Not supported

- **Azure Boards** administration: boards, sprints, iterations and area
  paths, custom field configuration, attachments, test plans and saved
  queries. Comments edited or deleted in Azure DevOps are not delivered as
  events (the service hooks do not report them).
- **Azure DevOps Server** (on-premises); only Azure DevOps Services at
  `dev.azure.com`.
- **Microsoft Entra ID OAuth and service principals**; only personal access
  tokens.
- **Pull request status / branch policy gate**: Preloop does not post a PR
  status or act as a required check.
- **Write flows** that push branches or open pull requests. Until they are
  supported, the pull request link above has no pull request to add.
- **Restricted CI identities** (for example a pipeline's build service
  account) as the tracker identity.
- **Old `{organization}.visualstudio.com` URLs**: these are refused with a
  message. Use `https://dev.azure.com/{organization}` and enter only the
  organization name.

## Application identities

Only PAT authentication is implemented. See the
[application identity investigation](azure-devops-application-identity.md)
for the requirements and remaining verification for Entra service principals
and managed identities.

Explicit-request bookkeeping retains the latest 256 comment signals per flow/PR.
Idle rows expire after 90 days without observation; pending work and live leases
are retained. Polling an open PR refreshes its label state so a label that still
needs manual removal does not expire and start another review.
